You wrote what looked like ordinary TypeScript inside a <script setup> block. A conditional type, maybe a mapped type over a generic. Vue threw it back at you:

// Component.vue
defineProps<T extends string
  ? { foo: string }
  : { bar: number }>()

✘ Unresolvable type: TSConditionalType

You searched. You found the docs, terse and a little resigned: the type to runtime conversion is still AST-based.

If you're new to Vue, you read that sentence and move on. If you've spent any time inside the framework, that sentence is a doorway. Walk through it, and a lot of the things you've been quietly working around start to arrange themselves into a single shape.

This is an essay about that shape. And about why — once you see it — you stop being angry at the error and start being grateful for what it's telling you.

I. The Misconception

It looks like TypeScript. It isn't.

The first thing to understand about defineProps<T>() is that it is not a function call, and the angle brackets are not, in any meaningful sense, generic parameters to a function. It's a compiler macro. The Vue Single-File Component compiler sees that call, and before any TypeScript checker has gotten near it, walks the AST of whatever you put between those brackets and generates a runtime props object from what it can read.

It doesn't evaluate the type. It reads the shape of the syntax. That distinction is doing all the work in this essay.

An object type literal? Readable. Pick<User, 'id' | 'name'>? Vue's resolver knows that one. A conditional type that has to be computed against an actual value of T? There is nothing to read yet — there is something to run, and the SFC compiler doesn't run types. It looks at them.

The Vue team is explicit about this in the docs. It isn't hidden, and it isn't accidental. It's a documented, deliberate boundary.

II. The Mechanism

Every Vue app has two type pipelines.

This is the load-bearing idea. Once you have it, every weird Vue typing behaviour you've ever fought with — every @vue-ignore, every "why does the editor know this but the build doesn't", every prop that mysteriously degrades to any — rearranges itself.

Pipeline one is the SFC compiler. It runs at build, it walks ASTs, and it has a bespoke type resolver that handles a deliberately limited subset of TypeScript. It is fast because it is shallow. It produces the runtime artifact — the actual props: { ... } object that Vue's runtime uses to validate and pass data.

Pipeline two is Volar (and vue-tsc). This one uses the real TypeScript compiler. It understands the full type system. It checks your templates against fully-resolved types at every call site. It is what your editor uses when it knows things the build doesn't.

These two pipelines do not share state. They look at the same file and see different things.

Once you internalise that, @vue-ignore stops looking like a hack and starts looking like exactly what it is: a comment that speaks to pipeline one and is invisible to pipeline two. It tells the SFC compiler don't try to read this, I'll handle the runtime declaration separately. Volar keeps enforcing. Your editor still knows. The split is the feature.

III. The Rule

Generics help when shape is invariant.

Here is the simple rule that falls out of all of this. A generic in <script setup> is fine when the runtime shape of your props is the same for every instantiation, and only the types of values flowing through the props vary.

// One runtime shape. T just decorates the values.
defineProps<{
  items: T[]
  selected: T
}>()

The compiler can emit one runtime declaration — { items: Array, selected: null } — that's valid for every conceivable T. The generic decorates the values that pipeline two sees; it doesn't change what pipeline one has to write down.

It breaks the moment the generic decides the shape itself. Whether a prop exists. Whether it's required. Whether the object has three keys or five.

// Two possible shapes. Compiler has to pick one,
// at component-compile time, before any consumer is known.
defineProps<T extends 'page'
  ? { route: string }
  : { handler: () => void }>()

The compiler doesn't know what T is yet — and it never will, from inside the component. The call sites that do know are on the consumer side, in other files, compiled later. From the component's vantage point, T is still abstract. There is no shape to write down.

"But I know what T is when I use the component." Yes — you do. The compiler doesn't. That asymmetry is the whole thing.

IV. The Escape Hatches

Three workarounds, three trade-offs.

You have three reasonable options when you hit this. They differ in where the type contract lives, and how strictly each pipeline enforces it.

Approach Lives in Runtime knows about prop? Enforcement Best for
Single conditionally-typed prop .vue Yes Type-only; can't forbid presence Minimal restructuring, soft contracts
@vue-ignore on the conditional .vue No — falls to $attrs Volar enforces fully Bridge / forwarding components
.ts factory .ts Per-bridge, fully Strongest, per-instance Multiple known cases, clean separation

Each is right for a different problem. The interesting thing is what they have in common: when the type contract can't live in the .vue file, you push it somewhere the unconstrained type system can handle it. The Vue file becomes a thin runtime; the contract lives at the boundary.

V. The Larger Thing

The Vue team didn't fail.

They made a choice. Early — before this problem existed in anyone's head — to keep the SFC compiler small, fast, and AST-based. That choice bought Vue something real: sub-second compile times, a tractable codebase, predictable behaviour, a story for tooling. It cost something equally real: the thing you just hit.

You cannot have both. No tool can.

A few months ago I read an essay called "Your Data Model Is Your Destiny." It sat in my head for a while before I understood why. The argument is that the early shape of a tool — its data model, its compiler architecture, its first abstraction — is the part that turns out to be hardest to change. Not because changing it is technically impossible, but because by the time the cost of the original choice is visible, the ecosystem around the tool has grown to depend on it. Every consumer is a vote for the status quo.

Tools differentiate themselves not by being more advanced. They differentiate by the idea at their centre.

The idea at the centre of Vue is: single-file components as the unit of work, runtime props as a first-class concept, templates that get compiled cheaply, and a compiler small enough that you can ship it everywhere. Everything else — every API, every limitation, every character trait of Vue — falls out of that.

The fact that you can't write a conditional type as your top-level props shape isn't a bug. It's a downstream consequence of choosing to compile props from syntax, not semantics. That choice is also why your Vue build is fast, why the runtime is small, why HMR works the way it does, why the framework is portable to environments where running a full TypeScript checker would be absurd.

You don't get to pick the consequences à la carte. The foundation chooses them for you.

VI. The Principle

First ideas are permanent.

The thing that makes a tool what it is — its first idea — is also the thing it cannot stop being. The earlier a choice was made in a project's life, the more of the project's identity is wrapped up in that choice. This goes well past frameworks. Languages, companies, products, institutions: the only ways a foundation actually changes are that the people change, or the project ends.

Vue's compiler is AST-based. React's reconciler is a tree diff. Svelte's whole pitch is compile-away-the-runtime. Rails picks convention. Django picks explicitness. Postgres picks correctness; Redis picks speed. These aren't features that got bolted on. They are the first ideas, and they radiate outward into everything those tools can and cannot do.

The skill — and I think this is the actual skill, more than any particular framework fluency — isn't picking the most advanced tool. It's recognising the kind of tool you are working with, what its foundation lets it do, and what its foundation will never let it do. Working with the grain instead of against it. Knowing when to push a problem up to a layer where the foundation no longer constrains you, and being willing to do so.

When you hit Unresolvable type: TSConditionalType, you are not hitting a bug. You are touching the load-bearing wall of the framework you chose. The right move is to step back and ask: is this still the right tool for this part of the problem?

Sometimes the answer is yes, with a @vue-ignore. Sometimes it's this contract belongs in a .ts file, not a .vue file. Sometimes — rarely — it's this whole concern doesn't belong in this framework at all.

The error is telling you something true. The framework is being honest about what it is. The only question is whether you're going to listen, or keep trying to make it be something it was never built to be.
